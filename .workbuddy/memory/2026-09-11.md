## 10:00-10:20（第三个会话）P1：客户端收到字面 `CALL_TOOL: Skill({...})`

### 现象与证据链
用户报"为什么返回了 `CALL_TOOL: Skill({...})` 这样的内容"。日志 `id=1631ecc9-23c6-4a95-ae60-386a7c4d5eff`：
```
[router-nocalls] upstream_text="NO_TOOL_NEEDED"
[req-trace] stage=answer_start prompt_len=151836 native_tools=0
[answer-tool] decision=call count=1 text_emitted=true      ← 既发了工具调用，又发了正文
chathub timing completion_frame_ms=12289 streamed_text=542 events=27
```
客户端会话存档（`~/.zcode/cli/rollout/model-io-sess_f083b481-*.jsonl`，按 `x-request-id` 命中）里 `response.text` **就是**那条 `CALL_TOOL: Skill({...})`，同时 `response.toolCalls` 有合法调用 —— 两者都到了客户端。
统计 24h：`decision=deferred_call`（抑制分支）**0 次**，`answer-tool decision=call` **1 次且 text_emitted=true** → 抑制路径 100% 未生效。

### 根因
`classifyAnswerOutputPrefix` 对**任何**既不等于 `call_tool:` 前缀、又不以 `{` 开头的缓冲就返回 `decided=true, isCall=false`。上游流式首包只有 **4 字节**（`first_delta_ms=... len=4` = `CALL`），于是第一包就把"不是工具调用"钉死 → 回撤闸门立刻放行 → `CALL_TOOL: ...` 整行进正文；尾部再按全文解析出 tool_call。**marker 的每一个前缀都会误判**，所以"看起来实现了抑制、其实从没运行过"。

### 修复（提交 10da981）
1. `classifyAnswerOutputPrefix` 增加 `isProtocolMarkerPrefix`：仍是 marker 合法前缀（`C`/`CAL`/`call_tool`/`CALL_TOOL`）时返回"未决"，继续缓冲。
2. 新增 `internal/web/answer_gate.go` 的 `answerProtocolGate`：开头缓冲到定论 + **全程滚动保留 16 字节尾窗**（跨包 marker 也不会漏出）+ 见到 marker 即锁定；`Flush()` 释放尾窗（极短回答不会被吞）。锁定后故意丢弃被抑制的字节——客户端侧解析用的是完整累积文本，与发射无关。
3. `server.go` 两条流式回答路径（**注意：本文件里有两套历史遗留的流式实现**，2257-2543 与 2663-2939，后者对 `stream=true` 不可达=死代码）都改用闸门；"protocol output failed validation" 分支不再回吐协议文本。
4. 测试：`TestClassifyAnswerOutputPrefix` 加 8 条前缀用例（先红后绿）；`answer_gate_test.go` 5 组用例（含**按 4 字节重放生产流**、散文严格逐字节不变、跨包 marker、极短回答不被吞、未装弹时透传）；`tests/live-answergate-20260911.py` 六组活体用例。

### 事故教训（可复用）
- **闸门的判定函数必须"前缀安全"**：流式首包只有 3-5 字节，任何"看到开头就下结论"的逻辑都会在首包误判。判据要写成"仍是候选前缀 → 未决"。
- 双保险：既要在开头拦住，也要在整流保留小尾窗，否则"散文在前、marker 在后"照样漏。
- 有 count=0 的分支日志（`deferred_call`）本身就是嫌疑信号：**没打过的日志 = 没跑过的代码**。
- 附带发现：`stage=http_start stream=%t` 读的是 **query 参数**，而实际分支走 `body.Stream`；ZCode 在 body 里传 stream，所以日志里的 `stream=false` 会误导排查（本次差点带偏）。

24h 统计：`upstream rewrote` **20 次**、`using final` **20 次**（100% diverged），其中 `186→787`（丢 76%）、`120→754`（丢 84%）、`1353→2796`（丢 52%）、`490→824`（丢 40%）是真实内容丢失；其余 16 次是客户端内容反而更多或只差 7 字节。
**修复**：diverged 时按 `commonPrefixLen` 补发 `final[lcp:]`（复用 client.go:238 已有的 rune-boundary 安全实现），开关 `M365_STREAM_DIVERGENCE_REEMIT=0` 回退。测试更新 + 新增 3 组（含用线上 186/787 真实串）。

### 缺陷二（新，P0）：**承诺式计划播报**没有任何守卫
模型输出"我会把…一起补齐"是**肯定式未来时承诺**，而现有三道守卫全是**否定式**：`isToolRefusal`/`containsToolDenial`（"没有工具/无法编辑"）、`isSandboxHallucination`（沙箱/code interpreter）→ 全部漏过 → 不触发 `[tool-eject]`。
**更关键**：`[tool-eject]` 重试只存在于**非流式**路径（server.go:2966-2982）；ZCode 实际走的 **twin A 流式路径（2257-2591）只有 `[answer-refusal]` 日志、没有重试**。
**根因链**：合成 user 消息 → 路由轮 `NO_TOOL_NEEDED` → answer 轮 `native_tools=0` → 只能靠文本协议 → 模型选承诺式散文 → 无守卫 → 零工具调用。

### **同一个坑第二次**：前缀安全 + `strings.ToLower` 的隐藏破坏
首包 4 字节是 `我\xe4`（"我会"的前 4 字节，**半截 UTF-8**）。`strings.ToLower` 对不完整 rune 会替换成 U+FFFD，**改变了字节前缀**，于是 `isPromissoryPrefix` 判定"不是承诺"→ 首包就放行 → 整个 guard 失效（与 10da981 的 CALL_TOOL 误判是同一类错误）。
**修法**：`utf8.ValidString(s)` 守卫 ToLower，无效时只做原串字节比较；另加 **24 字节固定未决窗口**兜底。回归测试钉死 `"我\xe4" / "我\xe4\xbc"` 必须判为前缀。
→ **教训固化：任何流式首包判定函数，只要用到 `ToLower`/正则/`unicode` 处理，都必须先过 `utf8.ValidString`。**

### 为什么"越修问题越多"（给用户的解释）
前几轮修的是**表达层**（协议行泄漏、拒绝措辞、连接身份），而**工具通道的开关在决策层**（路由轮）：`answer_start` 的 `native_tools` 恒为 0，工具只经路由轮下发，**路由轮判错 = 本轮没有任何工具可调**。路由轮是概率判定且只看 `tail=4` 的瘦身上下文，所以每出现一种新的失败"措辞"，就得再加一条短语守卫——补丁数量单调增长，但覆盖的是症状不是开关。
