## 图生图参考图上限 20 MiB → 5 MiB（提交 4ec0300，已部署）

用户要求：「图片上传改最大5MB吧」→ 追问后明确「图生图的参考图上限那里」。
（当时所在工作区是 `D:\code\GimageUI`，该目录**没有任何上传功能**；机器上唯一的「图生图参考图上限」在本仓库，
故改在此处。跨项目时先确认目标仓库，别猜。）

### 关键发现：一个常量被两种语义复用
`maxGeneratedImageBytes = 20 << 20` 同时承担：
1. **上传侧**：`imageEdits()` 里单张参考图的体积检查（`image exceeds 20 MiB`）；
2. **下载侧**：`designerDownloadError` 拉取上游生成图的上限。

**直接改这个常量会把 gpt-image-2 出图结果的下载也卡到 5 MiB（生成 PNG 经常超 5 MiB）**，属隐蔽回归。
故拆成两个常量，并加护栏测试锁死。

### 改动（`internal/web/images.go`）
- 新增 `maxImageEditImageBytes = 5 << 20`（单张参考图上限，两个入口共用）。
- `maxImageEditRequestBytes` = `maxImageEditImageBytes + (3 << 20)` = 8 MiB：
  5 MiB 图 base64 后 ≈ 6.7 MiB，留 3 MiB 给编码膨胀 + JSON/multipart 框架，
  否则合法 5 MiB 上传会先被 `MaxBytesReader` 413。
- 新增 `imageEditLimitError()`（两个入口共用同一文案，从常量推导）、
  `editAttachmentBytes()`（data: URL 解码后字节数；远程 URL 返回 0 交给 chathub 的下载上限）。
- **校验前移到 `resolveImageAccount` 之前**：原先 `operation=edit` 的「image is required」在账号解析之后，
  注定失败的请求也会轮换账号。顺带堵住「JSON 直连绕过 multipart 体积检查」。
- 两条入口都覆盖：multipart `/v1/images/edits`、JSON `/v1/images/generations` + `operation=edit`。

### ⚠️ 重大发现：本地仓库严重滞后，差点把线上回滚 3 天
- 服务器 `bak-pre-8c16e7a`、GitHub `ls-remote` 都显示 **GitHub main = 8c16e7a（9/12）**，
  而本地克隆停在 **a171c1b（9/09 22:34）**，中间 **40 个提交本地完全没有**（reflog 只有 1 条 clone + 1 条 commit，
  说明本地是 9/09 21:03 新克隆的副本，9/10–9/12 的活是在**别处**干的）。
- **教训（务必）：部署前先 `git ls-remote origin main` 比对，再决定从哪儿构建。**
  本项目备份命名约定 `bak-pre-<新提交>`，可用于交叉核对线上版本。本地 ref 有"读不准"的历史问题，一律以 `ls-remote` 为准。
- 取回方式：GitHub 本地当时不可达 → 在服务器 `git init --bare /tmp/relay.git` + `fetch` GitHub →
  本地 `git remote add relayssh ubuntu@…:/tmp/relay.git` → `git fetch --filter=blob:none relayssh main`
  → `git reset --hard 8c16e7a`。**用 git 自己的协议而不是 shell 管道**：
  `ssh host 'cat big.bundle' > file` 和 scp 都出现过截断/损坏（57MB 的 bundle 传下来大小相同但 sha256 不符、
  git 报 `pack has bad object`），只有 git fetch 可靠。
- 本地仓库因此变成 **blob:none 部分克隆**（promisor = relayssh）。之后 GitHub 恢复可达，
  已用 `git fetch --no-tags origin main` 补齐对象，使仓库重新完整。
