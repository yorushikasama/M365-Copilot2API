## WS_PROTOCOL 根因全面分析（09:00-09:30，用户要求先分析 new-api 再下结论）

### 根因（证据链闭环）
- gorilla v1.5.3 conn.go：`for c.readErr == nil` —— 任何读错误永久写入 readErr，后续所有读直接失败；并发读共享 bufio 与帧解析状态。
- 时序证据：hit age_ms=1316 → 1s 后 WS_PROTOCOL；0x4C('L')=FIN0/RSV2_1/opcode12，即 JSON 中间字节被当帧头。
- 违约点唯一：returnConn=true 仅 1403 行成功路径；fresh 连接由 Chat 私有 reader 读，Return→startPark 起第二个 reader，旧 reader 阻塞在 ReadMessage（Return 清 deadline 后永久阻塞+泄漏）。
- 量化：24h 1752 hit / 2156 warmed / 337 parked；WS_PROTOCOL 220 ≈ 命中即坏 12.6%。坏 conn 只咬一人（失败→Discard），但每个成功请求都埋新雷。
- awaitReaderExit 半方案证伪（deadline 唤醒=毒化；不唤醒=永久阻塞，两难）→ 已 revert。

## new-api 工具调用逻辑对比 + "两个一样的子任务"根因分析（10:15-10:45）

### new-api 的工具调用（/tmp/new-api 实证）
- **完全透传，零干预**：OpenAI 渠道 `ConvertOpenAIRequest` 不碰 `tools`/`tool_choice`（grep 无命中）；Claude 渠道 adaptor 同样不碰。工具只是 DTO 结构原样转发。
- 工具相关逻辑**只有计费**：`relay/channel/openai/helper.go` 流式里 `toolCount = len(choice.Delta.ToolCalls)`，最终 `usage.CompletionTokens += toolCount * 7`；`relay/common/tool_usage.go` 的 `ImageGenerationCallCounter` 用 id/call_id/index/result-hash 做**流式身份去重**（仅用于 image 计费）。
- **没有**"工具路由"层（不会额外发一轮 LLM 让模型决定调哪个工具），也不自建 MCP 暴露给上游。

### 我们的架构差异（这是温床）
1. 有 `model_tool_router`：额外一轮 LLM 决定工具，结果直接 `writeToolResponse` 返回（server.go:2101-2112）。
2. **工具双通道暴露（实锤）**：
   - 通道A：`clientPlugins()` 把客户端每个工具注册为 `Source:"API"` 插件（tools=16 → 16 个插件）。
   - 通道B：同时注册 `mcp-gateway` 插件，URL 由 `server.go:2013` 从**请求 Host 动态生成**（`%s://%s/v1/mcp/sse`），即指向本项目自己；而 `buildAnswerRequest` 又把**同一批工具** `MergeTools` 进 `GlobalToolRegistry`，MCP 的 `tools/list` 会返回它们。
   - → 上游模型看到两套同名工具。
3. **MCP 通道是僵尸**：`SetSessionTools` 从未被调用 → session.provider 恒为 nil → `tools/list` 能列出工具，但 `tools/call` 必然返回 `-32603 no tools available`。模型走这条必然失败，只能改走 API 插件通道重试。
4. **`GlobalToolRegistry` 只增不减**：`MergeTools` 每请求都调用，`ClearTools` 从未被调用 → 跨会话/跨用户累积历史工具，重名更多。
5. **router 成功路径无日志**（观测盲点）：只有 `len(calls)==0` 才打 `[router-nocalls]`，所以"48h 内 tool_calls_detected=0"是假象——工具调用全从这条静默路径出去了。
6. `parseModelToolDecision` **无去重**：模型输出 `{"calls":[X, X]}` 就产生两个 call（ID 用 index 区分，不会冲突）。唯一去重 `filterCompletedCalls` 依赖内存 ledger。
