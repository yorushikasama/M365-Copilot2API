## 429 链路代码审查 + 优化方案（docs/429-rate-limit-optimization-plan.md）
- 核心缺陷：resolveAccount(非空 ID) 跳过全部健康检查（server.go:1078→1118）；session-resolver/user-session/conv-cache/客户端 pin 都会把请求钉回不健康账号；clientPinnedAccount 一票否决 failover。
- 结果：客户端 72 次重试=72 次真实上游调用（每次 100KB）。修法：限流账号本地快速失败（429+Retry-After 不打上游）、metering remaining=0 冷却至 UTC midnight、resolver 解绑不健康账号、router prompt 瘦身（93KB→最近消息）、请求指纹防抖。
- 四阶段方案已写入 docs/429-rate-limit-optimization-plan.md，未动代码。

## 复核守卫修复（提交 461e898，仅注释+测试，二进制不变故无需重新部署）
- **更严谨的证明：守卫原为 100% 不可达**，不只是"配了 MCP 才跳过"。守卫需同时满足 `hasPlugins==false` 且 `len(defs)>0`；但 `clientPlugins()` 为每个**合法**工具注册插件，而 `defs` 非空同样需要至少一个合法工具 → `hasPlugins` 必为 true。两者矛盾 ⇒ 无论是否配 MCP gateway 都发不出去。
- 覆盖范围已确认，两条路径都有守卫：① 路由轮（server.go:2044）的 chathub.Request 未设 MCPServerURL/Tools/ExecutionAnchor，但 `clientPlugins` 走内置 Bing 兜底 → hasPlugins=true → 修复后路由轮也拿到守卫（此前同样没有，只有 modelToolRouterPrompt 末尾的锚点）；② answer 轮由 buildAnswerRequest 设 MCPServerURL(1741)+Tools → 同样覆盖。
- 守卫在 prompt **最前面**（withGuard 前置），而原来仅有的 executionAnchor 是**追加在末尾**（80KB prompt 尾部的一句话影响弱）——这是本修复可能奏效的关键（位置），不只是措辞更强。
- 已知行为副作用（可接受）：`clientPlugins` 在 tools 为空时兜底注册内置插件 ⇒ hasPlugins 几乎恒为 true ⇒ 普通无工具对话也会注入守卫（primed 成 agent）。本部署必配 MCP gateway，收窄条件无实际差异；部署后实测普通问候（12:39 "Hello AxonHub"）响应正常无异常。
- 测试准确性修正：`TestToolProtocolPromptNoToolsNoPluginsOmitsGuard` 传 hasPlugins=false 只覆盖退化分支（tools 全解析失败），**不代表生产"无工具聊天"**，已在注释中说明防止后人误读。
- 遗留风险：上游 M365 Copilot 自身有强身份（日志里自称"I'm M365 Copilot...powered by GPT-5"）且可能有自己的 system prompt，守卫只是 user turn 文本，属提示层缓解，不保证 100% 消除。需用户实跑验证。
