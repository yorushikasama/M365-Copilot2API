## 429 链路代码审查 + 优化方案（docs/429-rate-limit-optimization-plan.md）
- 核心缺陷：resolveAccount(非空 ID) 跳过全部健康检查（server.go:1078→1118）；session-resolver/user-session/conv-cache/客户端 pin 都会把请求钉回不健康账号；clientPinnedAccount 一票否决 failover。
- 结果：客户端 72 次重试=72 次真实上游调用（每次 100KB）。修法：限流账号本地快速失败（429+Retry-After 不打上游）、metering remaining=0 冷却至 UTC midnight、resolver 解绑不健康账号、router prompt 瘦身（93KB→最近消息）、请求指纹防抖。
- 四阶段方案已写入 docs/429-rate-limit-optimization-plan.md，未动代码。

## 对标 new-api（写入方案文档第六章）
- new-api 关键机制：入口多层限流（IP/用户/分组，Redis 固定窗口+令牌桶，429带Retry-After）、渠道优先级+权重选择、shouldRetry/processChannelError 错误分类（429重试不禁用，401/403禁用+通知）、channel-test 主动探活自动恢复、use_channel 轨迹日志、pre-consume/post-consume 本地记账。
- 结论：不能全面照搬（上游协议 WS会话+云对话归属 vs 纯HTTP无状态；配额在微软侧 vs 本地记账）。值得抄四样：入口限流中间件、冷却到期主动探活、failover轨迹日志+可配置重试数、管理员告警通知。

## 429 优化方案实施（阶段 1/2/3 核心落地）

## 阶段 4 收尾（可观测性 + 主动探活 + Allow-Failover 头）
- `throttle_stats.go`（新）：进程级指标注册表（仿 globalCircuit 单例模式），24h 滚动窗 + 200 条事件环；埋点五处：markAccountResult（上游真 429，按 ClassifyError==QUOTA_429 判定）、writeLocalThrottle（本地短路）、debounceReplay、nextHealthyAccountExcluding（failover）、探活成功/失败。API：GET/DELETE /api/throttle-stats（adminMiddleware 自动保护，非公开路径）。
- `throttle_probe.go`（新）：StartCooldownProber 后台探活（new-api channel-test 思路）。默认 60s（M365_PROBE_INTERVAL_SECONDS，下限 15s；M365_PROBE_ENABLED=false 关闭）。候选来源 accountHealth.ExpiredLimitedCooldowns——关键设计：该快照不做内联 cleanup（其他所有读者都会清理），否则 prober 永远看不到"已过期未清理"窗口。探活用最小 "ping" 请求复用 chatWithAccount（成功/失败自动流经既有健康记账），成功后 dropTransientConversation 防云对话堆积；GlobalCircuitIsOpen 时跳过 tick；每 tick 上限 8 账号 + cooldownProberGuard 防同账号并发探活。Vercel 入口（api/index.go）刻意不启动（与 StartAutoCleanup 同理，ephemeral 环境跳过长驻循环）。
- `X-M365-Allow-Failover: true/1`：解除 clientPinnedAccount 对 failover 的否决（首 attempt 仍打 pin 账号）。三路径（chatOnce/openaiChat/chatStream）统一接 handleCooldownGate：冷却账号 + 头存在 → nextHealthyAccountExcluding 换号（不烧干涸账号）→ 无健康备选才回本地 429。chatOnce 原本无短路，现在也补了闸门。

## 排查"agent 请求只回短话不执行"（用户走网关的 agent 客户端）
- 现象：用户在 agent 客户端发"对话管理加IP显示"，没执行只回短话。本机 WorkBuddy 会话存档/traces/daemon 日志均无此请求 → 请求走的是 M365 网关。
- 服务器日志定位：request 3642c03a，14:44:57（UTC 06:44:57），messages=62 tools=53 raw=267KB，model=gpt-5.6-sol，账号 xizu@office.bo.edu.kg，无 session-resolver 命中。
- 关键链路：router 轮 245KB prompt（88.5KB 会话+~157KB 工具schema/ledger）→ 8.8s 正常返回 → parse 成功但 calls=0（无 [tool-repair]/[tool-validation] 日志）→ 静默落入 answer 轮（142.7KB prompt + 53 native tools）→ 27s 后 200 返回 10.6KB 短文本。客户端把这段文本当最终回答展示 → "什么都没执行"。
- 根因：非 429 非报错，是上游模型在超大 router prompt 下没选任何工具、直接对话式作答。正是方案 3.1 要解决的问题（瘦身代码已写好未部署）。
- 观测盲点修复：router calls=0 时两路径（stream/non-stream）都静默落 answer，无任何日志 → 已加 [router-nocalls]（含 route_prompt_len/parsed/上游原文 300 字符），build+test 绿。
- 教训：排查用户"网关侧没反应"的问题先查服务器 journalctl 的 req-trace 全链路，别先翻本地工具日志；router 空决策此前完全不可观测。
